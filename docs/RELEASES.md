# Linux release bundles (draft infrastructure)

This describes the release packaging contract, not an available public release.
No public artifact is asserted to exist. The workflow creates **drafts only**,
and only after an explicit manual request and configured environment approval.
Adding this infrastructure does not upload, publish, install, or activate anything.

## Assets and compatibility

- `swiftwall-VERSION-linux-x86_64.tar.gz`
- `SHA256SUMS`: exactly one line, lowercase SHA-256, two spaces, archive basename,
  trailing newline. It hashes the compressed archive bytes.

`VERSION` is the same safe `major.minor.patch[-prerelease]` string in Cargo.toml,
manifest.json, and `bin/swiftwall --version` (`swiftwall VERSION` plus optional
newline). `0.2.0-dev` is accepted for local fixtures and unpublished build checks.
Draft publishing currently requires a stable version and an existing `vVERSION`
tag. The target is `x86_64-unknown-linux-musl`: a prebuilt Linux x86_64 daemon,
not an on-host Rust build. Python 3.11+ is required for packaging. The installer
uses the Python standard library; desktop/runtime prerequisites still apply.

## Exact archive and installer interface

`scripts/release_bundle.py` exposes `TARGET`, `ARCHIVE_PREFIX = "swiftwall-"`,
`archive_name(version)`, `archive_root(version)`, `validate_version(version)`,
`safe_path(name)`, `PLUGIN_FILES`, `SCRIPT_FILES`,
`SOURCE_FILES`, `PAYLOAD_FILES`, and `build_bundle(source, binary, output, version,
source_commit)`. The latter returns `(archive_path, checksums_path)` and refuses
existing outputs. Missing required source files fail closed; no recursive globbing
or automatic inclusion is used.

Every tar entry is a regular file below **one root, `swiftwall-VERSION/`**.
There are no directory entries, links, devices, FIFOs, absolute paths, `.` or `..`
components, duplicate paths, or backslashes. The fixed payload relative to that
root is:

```text
bin/swiftwall
swiftwall-setup
scripts/setup.py
scripts/setup_support.py
scripts/setup_download.py
scripts/install.py
scripts/install_support.py
scripts/uninstall.py

scripts/plugin_support.py
scripts/plugin_activation.py
scripts/service_control.py
scripts/deployment.py
scripts/evidence_support.py
scripts/validate_plugin.py
scripts/release_bundle.py
manifest.json
plugin/BarWidget.qml
plugin/FolderPicker.qml
plugin/Panel.qml

plugin/SettingsDraft.qml

```

The **eight-file plugin generation** is manifest.json plus the seven plugin/
files above. It is not eight plugin/ files plus a manifest. Tests, caches, images,
user configuration/state, build trees, and unrelated documentation are excluded.

`bin/swiftwall`, `swiftwall-setup`, and `plugin/pick_folder.py` have mode `0755`
(JSON integer `493`). All other files have mode `0644` (integer `420`). Source
permissions do not propagate into the archive.

The separately maintained top-level `swiftwall-setup` launcher is copied verbatim,
not generated by the packager. It must locate `scripts/` relative to its own
resolved location and make sibling setup/support imports work independently of
cwd (for example by adding that directory to sys.path before importing setup).
It must not assume a source checkout, `target/`, installed Python modules, or
that the user ran it from the archive root. Packaging unit tests use generated
fixtures. The separate candidate checker executes the actual extracted launcher
and binary from an unrelated working directory; it must pass on the real build
before that artifact is described as tested.

### release.json schema 1

```json
{
  "schema": 1,
  "version": "0.2.0-dev",
  "target": "x86_64-unknown-linux-musl",
  "source_commit": "1234567890abcdef1234567890abcdef12345678",
  "files": {
    "bin/swiftwall": {"sha256": "<64 lowercase hex digits>", "mode": 493},
    "manifest.json": {"sha256": "<64 lowercase hex digits>", "mode": 420}
  }
}
```

The abbreviated example omits the other payload entries. `files` is a mapping
from bundle-root-relative paths to **exactly** `{sha256, mode}` records for every
payload file **except release.json itself** (self-hashing is impossible).
`source_commit` is a full lowercase 40-hex Git commit SHA. The packager receives
it explicitly; CI derives it from the checked-out HEAD. For local builds, supplying
an SHA does not prove that the checkout is clean or that bytes came from that SHA.

A download verifier should validate the expected version, target, schema, source
identity policy, unique inventory keys, fixed allowlist, file modes, and hashes.
Reject duplicate JSON keys and unexpected archive entries, duplicate tar members,
non-regular members, unsafe paths, missing/extra files, and anything outside the
single expected root **before extraction**. Bound download, decompressed size,
member count, and metadata size independently; do not blindly use extractall.
`release.json` is the sole inventory exception and must have mode 0644. The
packager module is shipped at `scripts/release_bundle.py` with mode 0644 so the
download verifier can import the exact allowlists and safe version/path helpers.
Importing it does not build, install, or publish anything; build operations run
only when explicitly called. Changing the allowlist requires coordinating
packaging and download verification. Rechecking an extracted bundle also rejects
group/world-writable roots, subdirectories or non-sticky ancestors; bundle files
and directories must be owned by the invoking user. Root-owned sticky temporary
directories are permitted as ancestors. Extraction creates private directories
even with a permissive umask. Symlinks, hardlinked files and unexpected empty
directories are refused. These checks protect against other-user replacement,
not a hostile process running under the same UID. Download and verify the archive
before executing its helper, and extract into your own non-shared directory.

## Local packaging and tests

From the repository root, after the setup launcher and its support files exist:

```sh
cargo +stable test --locked --target x86_64-unknown-linux-musl
cargo +stable build --locked --release --target x86_64-unknown-linux-musl
python3 -B -m unittest discover -s scripts -p test_release_bundle.py -v
python3 -B scripts/release_bundle.py \
  --binary target/x86_64-unknown-linux-musl/release/swiftwall \
  --version 0.2.0-dev \
  --source-commit FULL_40_HEX_CHECKOUT_SHA \
  --output dist
(cd dist && sha256sum --check SHA256SUMS)
```

Install the musl Rust target and Linux musl linker/tooling first. Use the actual
Cargo/manifest version and literal checkout SHA, not the explanatory placeholder.
Use a fresh output directory. Before executing the binary or generating provenance,
`validate_elf(data)` checks the exact binary bytes to be archived using only Python's
standard library. It requires a complete 64-byte little-endian ELF64 header,
x86_64 machine type, ELF version 1, executable or static PIE type, and System V
or Linux ABI. It rejects scripts, other architectures, and **every PT_INTERP**
segment, including both GNU and musl dynamic loaders. The program-header table
must contain 1–128 entries of exactly 56 bytes (at most 7168 bytes), must start
after the ELF header, and must fit entirely within the binary. Extended header
counts are unsupported. Segment file ranges must fit the binary; load segments
must have sane memory sizes, nonoverflowing virtual ranges, valid alignment, and
an executable entry point. Section headers are not parsed. These are structural
checks, not a complete ELF loader, malicious-code sandbox, or proof of Linux-only
behavior.

The executable is then checked with a structured, no-shell `--version` subprocess,
a five-second timeout, nonzero-exit rejection, and a 4096-byte accepted-output
limit. Only run the packager on a trusted binary: this check executes it.
**A static glibc executable can pass these ELF checks; ELF does not prove musl
compiler/libc provenance.** The musl target claim relies on the reviewed CI build
command and build context, not solely on ELF inspection or local source_commit
input. The workflow establishes the intended target by compiling and testing it.
All packaging unit-test files, including shell version fixtures and non-executed
synthetic ELF files, are generated in temporary directories. Shell-fixture tests
mock only the ELF guard; separate tests exercise the real guard's rejection and
bounds. No real wallpaper images or live services are involved.

## Workflow, provenance, and release review

`.github/workflows/release.yml` supports manual (`workflow_dispatch`) execution
and build-only pushes to `dev/simplified-setup`. The narrow push trigger allows a
separately approved candidate-branch build without merging a newly added workflow
into the default branch merely to register manual dispatch. No push or workflow run
is authorized by adding this trigger locally. Its manual `publish` boolean defaults
to **false**; push events cannot enter the draft job.

Every run builds and tests the musl target with `--locked`, runs the offline
`test_release_bundle.py`, `test_setup_download.py`, and `test_setup.py` suites,
validates binary/Cargo/plugin version agreement, then executes
`scripts/check_release_candidate.py` against the real newly built archive. That
check verifies checksum, inventory, source commit, ELF and permissions; runs the
extracted launcher from an unrelated directory with no Rust toolchain in PATH;
and runs the extracted daemon with private state/socket/background and a fixture-only
fake setter. The archive, SHA256SUMS and `release-smoke.json` are uploaded as a
reviewable workflow artifact. This smoke is not full clean-user installation,
systemd or native-widget acceptance; those remain a separate downloaded-artifact gate.
Checkout and artifact actions use full SHA pins. Checkout shares offline.yml's
approved pin; artifact upload/download use pinned v4.6.2/v4.3.0 commits.
No third-party release action is used: the runner's GitHub CLI creates drafts.

To enable draft creation, administrators must first configure the `release-draft`
GitHub environment with **required reviewers** and appropriate tag restrictions.
An environment declaration alone does not create approval protection. Leave
publishing disabled until those protections are verified. Dispatch from the
existing `vVERSION` tag with `publish=true`; the read-only build job checks the
ref/version, and the separate environment-gated job gets `contents: write`.
That job downloads only this run's artifact, rechecks SHA256SUMS, and invokes
`gh release create --verify-tag --draft`. Existing releases are not edited and
assets are not overwritten. Public publication requires a separate deliberate
human action outside this workflow. No release or production actions are part
of local implementation/testing.

`release.json` records the declared source commit, version, target and exact
payload hashes/modes. The workflow/run logs additionally record the build context
and Rust, Cargo, and Python versions. This is **provenance information, not a
cryptographic provenance attestation**. Consumers should review the source tag,
workflow, and run; no signature or independent trust root is provided here.

Archive metadata is deterministic: sorted entries, regular files only, zero
mtime/UID/GID, empty owner names, fixed modes, USTAR headers, and a zero-timestamp
gzip header without an original filename. Equal input bytes on the same packaging
toolchain are tested to yield equal output bytes. This is **not a guarantee of
byte-reproducible Rust builds or identical compression across toolchains**:
runner images, Rust stable, system packages, and compression implementations can
change even though Cargo dependencies are locked. The ELF guard establishes
neither compiler identity nor byte reproducibility and cannot distinguish static
glibc from static musl; those limitations also apply to locally generated bundles.

**SHA256SUMS provides same-origin transport/download integrity, not a signature.**
An attacker able to replace both assets can replace both checksums. Neither the
inventory nor the checksum authenticates the publisher by itself. Do not describe
this release path as signed, independently verified, or fully reproducible.
