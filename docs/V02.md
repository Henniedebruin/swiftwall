# SwiftWall v0.2: widget, settings and local deployment

This development milestone adds an optional native Omarchy widget to the existing
Rust daemon. Supervised local deployment and manual controller acceptance have
passed. This is not a marketplace submission or public release. Machine-specific
reports, production configuration, state, backups and screenshots are not source
artifacts and remain excluded from version control.

## Architecture

- The Rust daemon remains the sole owner of carousel state, scheduling and wallpaper
  application. The QML widget never launches another daemon or sets wallpaper itself.
- The blocking daemon uses Unix-domain socket IPC, inotify and monotonic deadlines;
  no async runtime, renderer or Rust GUI framework is added.
- `plugin/Service.qml` instantiates `SharedService.qml`. The Omarchy service API shares
  that instance with `BarWidget.qml` and its lazily displayed `Panel.qml` controller.
- The plugin uses the existing Omarchy theme and UI components. It offers previous,
  pause/resume, next, interval/mode settings, folder drafts, Save and Revert.
- The bar countdown is optional. A local timer advances visible countdowns from
  subscribed deadline snapshots; no continuously running status subprocess polls.
- Explicit pause and protective suspension are distinct. Both offer Resume; recovery
  clears protective suspension only after the daemon verifies a safe background state.
- Manual wallpaper changes reset the countdown without clearing an explicit pause.

The default endpoint is `$XDG_RUNTIME_DIR/swiftwall/control.sock`. An explicit
`SWIFTWALL_RUNTIME_DIR` overrides it, including for the QML service. The shell must
inherit the intended environment when it starts; a CLI environment change does not
retroactively change a running shell. Production installations should not inherit
private test overrides.

## Settings and protocol

Legacy CLI commands and status responses remain available. Versioned JSON requests
use `swiftwall request` and a newline-framed Unix socket:

```sh
swiftwall settings
swiftwall request '{"v":1,"id":"inspect","op":"hello"}'
swiftwall request '{"v":1,"id":"settings","op":"getsettings"}'
```

`hello` negotiates `protocol_version`, `daemon_version`, capabilities, settings and
revision. The current capabilities include `settings`, `subscribe` and `sequential`.
The legacy `status` CLI envelope must not be used to infer negotiated metadata.
A versioned status request includes metadata; the deployment checker uses that path.

Settings contain `interval_seconds`, `selection` (`shuffle` or `sequential`) and
`folders`. `updatesettings` requires `if_revision` from the last settings snapshot.
Stale revisions fail rather than overwriting another writer. `validatefolders`
checks candidate roots without saving them. New roots must be readable local
folders; unavailable existing roots can remain configured. New network/GVFS/FUSE
roots are rejected, including local FUSE filesystems.

The widget keeps edits in `SettingsDraft.qml`. Picker acceptance and folder removal
only change that draft. Save sends a validated transaction; Revert reloads saved
settings. Cancellation never saves. A successful save atomically replaces the TOML
configuration, so original comments/formatting are not retained. A durability warning
means a rename may have committed without confirmed directory sync; inspect the
reported settings before retrying. No partial configuration is intentionally written.

Path handling rejects ambiguous symlink/`..` failures rather than silently choosing
another folder. Spaces, Unicode, quotes, `#` and `%` are supported. State schema 1
retains carousel history, shuffle selection and pause through compatible restarts.
Mode changes retain the shuffle bag. v0.1 does not accept sequential configuration;
rollback must restore compatible shuffle TOML before starting that version.

## External folder picker

`plugin/FolderPicker.qml` launches `plugin/pick_folder.py` only on Add Folder. The
helper uses Gio's session D-Bus connection and the XDG Desktop Portal FileChooser
interface. It is a separate short-lived process, not an in-process Qt folder dialog.

Runtime requirements:

- `/usr/bin/python3` and PyGObject/Gio (`python-gobject` on Arch).
- A working session bus, XDG Desktop Portal and a FileChooser backend.
- The existing Omarchy/Quickshell environment and its QML modules.

No dependency is installed automatically. The engine itself does not depend on
Python. The helper handles response signals, cancellation, local URI conversion,
parent-window input and bounded completion. QML uses structured process arguments,
a single-dialog guard, streaming output limits and timeout cleanup. A helper crash
cannot directly terminate the hosting Quickshell process. Native focus and chooser
behaviour still require user-operated acceptance on the target desktop.

## Installation boundaries

See [engine installation](../packaging/INSTALL.md) and
[plugin file lifecycle](../packaging/PLUGIN_INSTALL.md). These are separate tools:

1. Build and review the Rust binary and configuration.
2. Install the engine and user unit with `scripts/install.py`.
3. Start the existing `swiftwall.service`, verify bounded versioned readiness,
   socket peer ownership, running executable and recovered state.
4. Install/verify the eight-file production plugin using `scripts/plugin_install.py`.
5. Explicitly enable `io.github.henniedebruin.swiftwall` through Omarchy's supported
   plugin mechanism. Preserve existing entries and plugin settings.
6. Verify actual widget connectivity and usable status/controls, not only registry
   discovery or a separate CLI probe. Complete manual panel and chooser checks.

File installers do not enable the widget, start a daemon or alter wallpaper folders.
The service uses `graphical-session.target`; upgrading need not disable autostart.
Stop the service gracefully and capture a verified stopped-state backup first.

`scripts/deployment.py` provides the tested `Deployment` coordinator, not a default
live CLI. A reviewed caller must explicitly supply home, selected unit, environment,
artifact hashes, backup/evidence locations and activation controller. It supports a
first plugin installation, not generation-aware updates to an already installed
widget. Never blindly rerun it over an existing plugin installation.

The coordinator requires a **preconfigured, loaded** unit with explicit matching
`Environment=` values for `HOME` and all five `SWIFTWALL_*` engine overrides
(config, state directory, runtime directory, background link and setter command).
The setter and all destinations must be absolute paths. Passing an environment
to `systemctl` does not configure a service. The coordinator reads the selected
unit's `Environment`, `EnvironmentFiles`, `PassEnvironment`, `UnsetEnvironment`
and `PAMName` before any engine probe, stop or installation, and again before
each start and health check. Missing/mismatched values, additional SwiftWall
overrides, environment files, pass/unset directives and PAM injection are refused.
Ambiguous or C-escaped `systemctl show` output is also refused; these forms are
outside this conservative coordinator contract even if systemd supports them.
No automatic drop-in is created. The stock file-only unit remains usable for
manual activation, but needs separately reviewed preconfiguration to use this
coordinator. This is an intentional restriction of supervised deployment tooling,
not a new daemon requirement.

Service-property query stdout/stderr stay in memory for validation and are omitted
from coordinator events and rehearsal traces on success, nonzero exit and runner
failure. Environment errors use fixed diagnostics without echoing unit values or
untrusted variable names. Evidence directories are restricted to `0700` and these
logs to `0600`, including existing permissive paths; existing entries are retained.
Symlinked evidence paths and symlinked, multiply linked or nonregular log files
are refused.

Before issuing health IPC, the coordinator also compares the running MainPID's
`/proc` environment with those values and rechecks PID stability. Unit commands
and any launch wrapper remain trusted, reviewed inputs: wrappers that change
engine destinations are unsupported. Concurrent unit/manager edits and hostile
same-user programs are outside this nontransactional contract; do not change
service configuration during deployment. The isolated rehearsal now declares
matching unit `Environment=` values and retains its independent execve isolation
guard. Its systemd scenarios were not run during the latest offline hardening.

The coordinator verifies engine ownership, preserves autostart, backs up stopped
state, installs once and waits for bounded IPC readiness. The activation controller
sets `OMARCHY_SHELL_IPC_TIMEOUT=10s` for activation-related subprocesses, with a
12-second outer bound. It sends at most one enable request and reconciles the live
registry, effective bar and persisted settings after errors or timeouts. A lost reply
is not proof of rejection; never automatically send another enable request.

On critical failure, the tested coordinator restores the owned v0.1 engine and
compatible configuration and checks its health. Latest compatible state is retained
rather than replaced with stale history. It preserves the active wallpaper. If widget
cleanup is ambiguous or unrelated settings changed, it restores the engine where
safe, retains plugin/evidence files and reports cleanup pending instead of overwriting
unrelated bar settings. Keep an independent verified backup: installer rollback has
only one previous-generation slot and consumes it.

## Preview and lifecycle lessons

The preview utilities are development tools, not production dependencies:

- `preview_bundle.py` generates unique temporary IDs, fresh component URLs and
  pinned private endpoints in both service entrypoints.
- `preview_ownership.py` records the exact eight-file payload and refuses deletion
  of unknown or modified files.
- `preview_proxy.py` records bounded private IPC with peer-PID checks.

Rewriting QML at an already loaded URL can leave stale components in a long-running
shell. Native previews must use a fresh namespace, never the production plugin ID.
Registry activation and CLI health alone cannot prove that a widget chose the correct
socket. Test ownership, connection, handshake, subscription and panel usability.
Cleanup must remove only the preview's entries and files; never restore a whole old
shell configuration over concurrent user changes. Do not restart the desktop to
mask an unresolved loading or focus problem.

## Validation

See [PUBLIC_READINESS.md](PUBLIC_READINESS.md) for the latest results and blockers;
the historical live acceptance above does not validate these hardening changes.

Run from the repository root with Rust stable and the installed QML tooling:

```sh
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
python3 -B -m unittest discover -s scripts -p 'test_*.py'
python3 -B scripts/validate_plugin.py
python3 -B scripts/test_widget.py --binary target/debug/swiftwall
cargo build --release --locked
```

Python discovery includes ownership-aware installer/rollback, activation, service
control, preview isolation, picker subprocess and protocol regression tests. The
widget harness uses private fixtures/fake setters and offscreen QML. Packaging tests
use temporary homes. `scripts/rehearse_deployment.py` separately exercises actual
release binaries/installers and disposable systemd user services; its arguments must
point to verified artifacts and a private evidence location. Never substitute the
production endpoint in an isolated test. Native chooser tests require manual input;
headless tests do not establish real-shell focus or visual correctness.

## Known limitations

- Uninterruptible kernel filesystem I/O cannot be cancelled by a userspace timeout.
  Settings work is bounded so stalled workers do not create unbounded concurrency;
  a stalled operation can retain a slot and require recovery before more work proceeds.
- An atomic persistence operation already entered by a worker may have an uncertain
  outcome. Observe authoritative state rather than assuming timeout means no commit.
- Plugin tree/metadata replacement is not a multi-path power-loss transaction.
  Keep retained recovery data on inconsistent ownership or interrupted transactions.
- Omarchy's setter has no compare-and-swap or visual-display acknowledgement. The
  daemon reconciles observed changes but cannot eliminate every external setter race.
- The panel currently has no aggregate eligible-image-count label. `swiftwall status`
  reports the total. No thumbnails, previews or per-monitor controls are included.
- Process-local resource use can be sampled, but whole-shell CPU/RSS also includes
  other plugins and allocator history; it is not an isolated widget benchmark.
